<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| existing target file → init module | Untrusted user-edited content is parsed by `scanBlock` and hashed by `computeFingerprint` |
| existing marker block body → fingerprint preimage | The body string is hashed; the hash drives the hand-edit guard decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05 | Tampering | hand-edited marker body | mitigate | SHA-256 fingerprint stored as start-marker attribute (outside the hashed body) — `verifyFingerprint` detects body tampering before any overwrite (INIT-07) |
| T-07-06 | Spoofing | attacker forges fingerprint attribute | mitigate | The fingerprint is a content hash, not an HMAC — but Phase 7 explicitly defines this as an integrity-only signal, not security. If an attacker has write access to the target file they already have write access; the guard is for accidental hand-edits, not adversarial tampering. Documented in RESEARCH security domain. |
| T-07-07 | Information Disclosure | regex backtracking on malicious input | accept | `BLOCK_PATTERN` uses non-greedy `[\s\S]*?` with bounded structure (markers must appear); no catastrophic backtracking possible on Node's RE2-style engine since v18 |
| T-07-08 | Tampering | LF/CRLF round-trip producing `\r\r\n` | mitigate | `applyEolBom` always normalizes to LF first, then converts to target EOL (RESEARCH Pitfall 1) |
| T-07-09 | Denial of Service | extremely large body fed to `createHash` | accept | Linear-time hashing; size bounded by target file size (agent instruction files are KB-scale) |
</threat_model>
