## Trust Boundaries

This plan extends the IR schema (a wire-protocol-adjacent surface, since the envelope is serialized to MCP clients). The trust boundary is the `attributes[*].value` string, which originates from user source code (already trusted by the parser) and is now passed through to the envelope.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-10-01 | Information Disclosure | Literal JSX prop strings now exposed in envelope | accept | All values originate from the same source files the envelope already exposes via `kind:"text"` nodes; no new disclosure class. The user explicitly opted in by pointing the analyzer at their project. Privacy carve-out (D-12) does not apply — that's UAT-evidence-only. |
| T-06-10-02 | Tampering | Optional `attributes` field accepted by zod could be set by a malicious client passing a hand-crafted envelope back through any future inverse path | accept | No inverse path exists in v1 (envelope is server→client only). The schema's `.optional()` plus typed shape `Array<{name, value}>` is enforced; injection of unexpected types would be rejected at parse time. |
| T-06-10-03 | Backward compat (D-15) | Existing v1 clients parsing the envelope encounter an unknown field | mitigate | Field is OPTIONAL and additive; `schemaVersion: "1"` retained per Standard Schema additive-evolution rules. Existing clients ignore unknown fields by default (zod parsers built from the previous schema would simply not consume `attributes`); no client breakage. |
